# ---- reproducibility: lower bounds are not pins ----------------------------------------
# The bounds below say what the code REQUIRES. They do not make two machines agree to the
# last digit, and it is worth knowing exactly how much they do not.
#
# MEASURED 2026-09-04, same code, same reused CREST directory, minutes apart,
# dsgdb9nsd_000018 -- old split environment (MKL, torch 2.7.1, mace 0.3.17) against the
# new single environment (OpenBLAS, torch 2.13.0, mace 0.3.16):
#
#     electronic energy      identical to 4.6e-10 eV
#     lowest frequency       79.715281 vs 79.692059 cm-1   (2.3e-02)
#     G - Eel                35.5091567 vs 35.5089401 kcal/mol  (2.2e-04)
#
# 2.2e-04 kcal/mol is 230x below the CREGEN energy condition (0.05) and ~450x below this
# branch's target precision. Nothing here changes a basin, a sigma or a ruling.
#
# AND THE CAUSE IS NOT THE BLAS. Isolated separately, so neither could hide behind the
# other:
#     eigenvalues of a fixed seeded symmetric matrix   agree to 1e-14   (LAPACK)
#     MACE energy on a FIXED geometry                  identical, d = 0 (potential)
#     MACE forces on that geometry                     agree to 8e-16
# What is left is the optimiser: a 1e-15 force difference, iterated ~125 BFGS steps,
# converges to a different point INSIDE the fmax = 1e-4 eV/A tolerance, and the softest
# mode -- a second derivative -- is where that shows up first.
#
# So: for ordinary use, the bounds are right. If you need bit-identical numbers across
# machines, pin `torch==` and `mace-torch==` to the versions in your product records --
# every record written by this repository carries both (`engine/torch_version`,
# `engine/mace_torch_version`), which is why it carries them.
