## (a) How mace resolves a model

**`MACECalculator` never downloads and never hashes.** `openQHA-Hessian/mace/calculators/mace.py`:
- `model_paths` (str treated as a glob, a `Path`, or a list) or `models` (in-memory module(s)) — exactly one — mace.py:157-160, 213-234. Empty glob → `ValueError: Couldn't find MACE model files` (mace.py:215-217). Docstring: "to make a committee use a wild card notation like `mace_*.model`" (mace.py:86-88). >1 path → committee with `energy_comm`/`energy_var`… (mace.py:237-250 in 0.3.16).
- Each path is loaded with plain `torch.load(f=model_path, map_location=device)` (mace.py:226). No checksum, no version check (`git grep -i sha256 v0.3.16 -- mace` → 0 hits; `checksum` → 0; grep over `mace/calculators/` for `__version__` → none).
- dtype/device defaults: `device="cpu"`, `default_dtype=""` → adopt the model's dtype with a warning; `float64`/`float32` convert via `.double()`/`.float()` (mace.py:103, 307-320).
- `mace/__init__.py` sets `os.environ["TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD"] = "1"` (v0.3.16, still in main) — the full-module `torch.load` above only works on torch ≥2.6 because of this (env here: torch 2.12.1).

**Helpers `mace_off()` / `mace_mp()` add download+resolve** (`mace/calculators/foundations_models.py`):
- `mace_off(model=None|"small"|"medium"|"large")`: URL table at foundations_models.py:111-115 → `raw.githubusercontent.com/ACEsuit/mace-off/main/mace_off23/MACE-OFF23_{small,medium,large}.model`; cached under `get_cache_dir()` = `$XDG_CACHE_HOME/mace` else `~/.cache/mace` (mace/tools/utils.py:170), file name = URL basename → `MACE-OFF23_medium.model`. Any `https:` string or an existing local path is accepted; a missing local path raises `FileNotFoundError` wrapped as `RuntimeError` (foundations_models.py:362-430). Defaults `default_dtype="float64"`, device = CUDA-if-available. Prints the ASL acceptance text when it downloads (foundations_models.py:399-405).
- `mace_mp()`: if the *bundled* `foundations_models/mace-mpa-0-medium.model` exists it is used (foundations_models.py:86-89, 143); default dtype float32 (foundations_models.py:238). Download goes to the same cache (foundations_models.py:129-175).
- `mace_anicc()`: bundled `foundations_models/ani500k_large_CC.model`, else downloads into the package directory itself (foundations_models.py:449-478).

**Bundled files absent — this fork's normal case, and upstream's wheel case.** The fork's base commit deleted exactly three binaries: `2023-12-03-mace-mp.model`, `ani500k_large_CC.model`, `mace-mpa-0-medium.model` (git `diff v0.3.16 base-v0.3.16`); `mace/calculators/foundations_models/` here holds only `mp_vasp_e0.json`. Consequences: `mace_mp()` falls through to the download branch; `mace_anicc()` downloads; `mace_off()` never used bundles. Upstream documents the same situation for the wheel: "the tracked checkpoints are **in git but not in the wheel** … the published wheel is ~300 KB and holds `foundations_models.py` without the directory of the same name … `local_model_path` points at nothing and `mace_mp()` would *download*" (`ACEsuit/mace@main:tests/golden/docs/foundations.md`). The fork's `tests/test_foundations.py:28-33,410-459` still parametrise over the deleted path (not executed here).

**Checksums/version checks: none at load; upstream pins artifacts only in its own golden tests.** Upstream main has no hash in `foundations_models.py` either; it added download sanity checks only (Content-Type rejection + `_discard_cached_download`, main `foundations_models.py`). Its reproducibility pin lives in the test harness: `tests/golden/foundation_artifacts.py` records a `sha256` per checkpoint, and `tests/golden/test_foundation_goldens.py` digests "the file the loader actually opened — observed by watching `torch.load` during the loader call", failing "this is not the artifact this golden pins" (GitHub code search, 2026-09-26; `tests/golden/docs/foundations.md`).

## (b) How a fine-tuned `.model` is loaded

- The `.model` container is a **full pickled `torch.nn.Module`** (`torch.save` zip), not a state_dict: training ends with `torch.save(model_to_save, …/<name>.model)` plus a `jit.compile`/`torch.jit.save` attempt (v0.3.16 `mace/cli/run_train.py:1077-1114`). Loading is `torch.load(path, map_location=…)`; `MACECalculator` does exactly that, and openQHA's two custom loaders do it directly: `parameter_fingerprint` (`openQHA/openqha/potentials/engine.py:393-407`, `weights_only=False`) and the OpenMM route `_load_model` (`openQHA/openqha/quasi_harmonic/openmm_mace.py:56-63`).
- **`--E0s` is a training flag, not a load flag.** E0s live inside the model (`atomic_energies_fn.atomic_energies`; read for `--E0s foundation` at `run_train.py:464-472`). Choices: `"average"`, a `.json` path, a literal dict (`mace/tools/scripts_utils.py:579-611`), `"foundation"` (copy the foundation model's E0s buffer) and `"estimated"` (fit E0s from foundation predictions, `mace/data/utils.py`–`estimate_e0s_from_foundation`; both in v0.3.16, `run_train.py:453-500`). Nothing in `mace/calculators/` accepts E0s. openQHA trains with `--foundation_model <path> --E0s foundation` so a fine-tune cannot move the energy zero (`openQHA/openqha/training/run.py:380-383`).
- dtype/device at load: helpers default `mace_off`→float64, `mace_mp`→float32, device CUDA-if-present; calculator defaults cpu/adopt-model-dtype. openQHA always passes `default_dtype="float64"` and records it (engine.py:186, 415-433).

## (c) MACE-OFF23 distribution conventions

- `ACEsuit/mace-off` (main) contains `README.md`, `LICENSE.md`, `mace_off23/` = `MACE-OFF23_{small,medium,large}.model` + `MACE-OFF23b_medium.model` + `train_scripts/`, and `mace_off24/MACE-OFF24_medium.model` (GitHub contents API, 2026-09-26). `MACE-OFF23_medium.model` is 18 350 596 bytes — the byte count openQHA's pin comment records (`engine.py:153`). `MACE-OFF23-SC` is **not** in this repo.
- License: Academic Software License — "free to use them for academic purpose, but not for commercial purposes" (mace-off `README.md`, `LICENSE.md`); `mace_off()` prints the same terms on download.
- Recommended loading lines (MACE docs, "Foundation models"): `from mace.calculators import mace_off` … `calc = mace_off(model="medium", device='cuda')`; the models table links the three OFF23 files to the GitHub repo and cites arXiv:2312.15211. The docs show HuggingFace links for MACE-universal and mace-mh-1 only — **no HF channel is documented for MACE-OFF23**.
- `mace_off()` keys cover only small/medium/large OFF23 (foundations_models.py:111-115, unchanged on main); OFF23b/OFF24 have raw URLs but no key — though `mace_off(model="<https url or local path>")` accepts either (foundations_models.py:362, 388-403).

## (d) Implications for openQHA (facts above; judgement flagged)

Current surface (this checkout): `ENGINES` = filename/source/note + optional `params_sha256` (only `MACE-OFF23_medium`, engine.py:143-179); `model_path()` resolves one flat dir with `S0_MACE_ROOT`/`S0_MACE_MODEL` and raises a guidance `FileNotFoundError` otherwise (engine.py:111-148, 201-246); `calculator()` **already calls mace natively** — `MACECalculator(model_paths=<path>, device=…, default_dtype="float64")` — then runs `check_weights_are_physical` (engine.py:415-437); `provenance()` computes a state_dict SHA-256 and *reports* matches/differs/unpinned (engine.py:250-322, 368-407); `--pin` prints a paste-able registry entry carrying `params_sha256` (`openQHA/scripts/tooling/s0_check_weights.py`).

- Fact: the pin is already **report-only** — a mismatch WARNs and lands in the record, never refuses (engine.py:280-290). The only load-time refusals are a missing file and `check_weights_are_physical`, a magnitude ceiling (1e6) unrelated to identity or bytes (engine.py:440-506). `S0_MACE_ROOT`/`S0_MACE_MODEL` are path overrides, also orthogonal to hashing.
- Fact: mace's native surface takes a local path directly (`MACECalculator(model_paths=…)`, `mace_off(model=…)`, `mace_mp(model=…)`); only the helpers download, only for their known keys/URLs; both refuse a missing local file (ValueError / RuntimeError) — neither hashes anything.
- So "remove SHA256, call models natively" could concretely mean (decision is ticket 04's): **(i) minimal** — keep registry, flat dir and overrides; delete the `params_sha256`/fingerprint/pin plumbing (`fingerprint_state_dict`, `parameter_fingerprint`, `_FINGERPRINTS`, `params_pin_status`, the `--pin` pin line, training hash fields) and load exactly as now, because the load path is *already* the native call; **(ii) delegate resolution to mace** — `mace_off(model=<path or raw URL>)` could replace the flat-dir lookup for the OFF family (raw URLs exist for 23/23b/24), moving downloads/caching to `~/.cache/mace`; MACE-OFF23-SC would still be an operator-supplied local file, and on a cluster the ASL notice/download behaviour is a real change (offline Tianhe).
- Flagged judgement (not decided here): whether `check_weights_are_physical` and the env overrides survive; whether the registry keeps `filename`+flat dir or defers to mace wholly; which provenance fields replace the fingerprint. Note upstream's own precedent: hashing lives in the *test* tier that claims byte reproducibility, not on every user load (`tests/golden/docs/foundations.md`).
